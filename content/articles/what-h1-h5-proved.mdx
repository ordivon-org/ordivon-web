<h2 id="the-experiment-was-not-a-provider-benchmark" data-toc="Not a Provider benchmark">The experiment was not a Provider benchmark</h2>

<p>H1–H5 asked an architecture question: can one durable Task survive materially different Agent Harnesses, physical execution, stale workers, missing deliverables, and ambiguous responses without making a Provider Session or Runtime process the source of truth?</p>

<p>The answer was yes within one frozen repository-repair workload. The answer came with deletion: no universal Provider Session, common Tool lifecycle, Harness database, Runtime Task state, or shared event runtime was justified.</p>

<div className="article-thesis"><p>The decisive result was not that Codex and Hermes behaved the same. It was that the Task remained coherent while they behaved differently.</p></div>

<h2 id="h3-and-h4-proved-that-harnesses-are-materially-different" data-toc="H3 and H4: different Harnesses">H3 and H4 proved that Harnesses are materially different</h2>

<div className="provider-result-strip" aria-label="H3 and H4 live measurements">
  <div><strong>27,325</strong><span>Codex reported tokens</span></div>
  <div><strong>259</strong><span>Codex Provider messages</span></div>
  <div><strong>35,992</strong><span>Hermes reported tokens</span></div>
  <div><strong>689</strong><span>Hermes Provider messages</span></div>
</div>

<p>The H3 Codex Run used CLI/App Server revision 0.145 and model <code>gpt-5.6-sol</code>. It created one real Thread and Turn, executed one successful read command through a Runtime-managed process tree, emitted usage and Tool events, and left the Host Task waiting.</p>

<p>The H4 Hermes Run used Agent 0.18.0, ACP v1, and <code>deepseek:deepseek-v4-pro</code>. It emitted 449 thought chunks, 234 message chunks, two usage updates, and one read Tool observation. No Tool completion update appeared after the Tool start. The Prompt still ended successfully, and the Task still remained waiting.</p>

<p>A code audit found approximately 841 lines in the Codex direct driver and 947 in Hermes, with an exact-line Jaccard similarity near 0.275. Most overlap was subprocess, queue, parsing, validation, serialization, and receipt mechanics. The lifecycle was not common enough to justify a universal implementation.</p>

<h2 id="h5-ran-both-replacement-orders" data-toc="Both replacement orders">H5 ran both replacement orders</h2>

<p>The frozen workload contained a deterministic largest-remainder allocation defect, a versioned specification, immutable tests, and two required Artifacts: <code>diagnosis.json</code> and <code>completion.json</code>.</p>

<pre tabIndex={0}><code>{`Codex diagnosis → Host Assignment generation 2 → Hermes repair
Hermes diagnosis → Host Assignment generation 2 → Codex repair`}</code></pre>

<p>Each trajectory kept one Task Attempt, compiled fresh Context, passed the diagnosis through Host-retained Artifact evidence, started a new Provider Session, ran independent Runtime acceptance, and let Host alone commit <code>TaskOutcome</code>.</p>

<p>The two replacement orders produced different source digests:</p>

<ul>
  <li><code>sha256:1fb2d560fa109be2673b3d1834df8a441b6c88541b47fdd3c214a3bfd6095ebd</code></li>

<p>Both satisfied the same frozen specification and acceptance tests. Semantic completion therefore bound diagnosis, required Artifacts, final source digest, and independent verification—not byte-identical implementation.</p>

<h2 id="fault-one-stale-assignment" data-toc="F1: stale Assignment">Fault one: stale Assignment</h2>

<p>After Assignment generation 2 was committed, the generation-1 diagnosis Harness proposed that the Task was complete. Both stale proposals were retained and rejected as <code>stale_assignment</code>. The acceptance verifier did not run, no Runtime Job was dispatched by stale adjudication, and no TaskOutcome was created.</p>

<p>This retained Assignment generation as a durable semantic fencing token. Task revision describes Task state; Assignment generation describes which current execution commitment may submit evidence.</p>

<h2 id="fault-two-process-success-without-artifact" data-toc="F2: success without Artifact">Fault two: process success without Artifact</h2>

<p>A real Runtime process exited successfully and produced terminal evidence but did not create the required completion Artifact. Host rejected <code>missing_artifact</code>, skipped acceptance verification, and left the Task waiting.</p>

<blockquote>Physical success is evidence. It is not semantic completion.</blockquote>

<p>This retained <code>CompletionProposal</code> and <code>CompletionDecision</code> as an admission boundary distinct from process state and TaskOutcome.</p>

<h2 id="fault-three-response-loss" data-toc="F3: response loss">Fault three: response loss</h2>

<p>The successful response to the Codex→Hermes repair dispatch was deliberately dropped. A fresh Host recovered exactly one original Runtime Job through the Assignment-bound request identity and opaque Host references:</p>

<pre tabIndex={0}><code>{`dispatchCalls = 1
matchingJobs = 1
responseLost = true`}</code></pre>

<p>No repair was blindly redispatched. This retained Host/Runtime request identity and rejected a Runtime Task table or semantic query platform.</p>

<h2 id="the-final-message-failed-as-a-contract" data-toc="Final text failed as a contract">The final message failed as a contract</h2>

<p>Both Codex Runs returned usable structured final responses. Both Hermes Runs completed Tools, wrote valid Artifacts, and passed independent verification while ACP final assistant text was absent.</p>

<p>The first orchestration attempt treated missing final text as failure. Inspection showed that the work was already correct. The worker was changed to Artifact-first completion: Provider text became optional observation, and the canonical result was reconstructed from verified Artifacts when text was missing or structurally unusable.</p>

<p>This was not a workaround for Hermes. It exposed a general systems error: language about completion is less authoritative than the state and evidence that completion requires.</p>

<h2 id="what-h1-h5-did-not-prove" data-toc="What H1–H5 did not prove">What H1–H5 did not prove</h2>

<ul>
  <li>It did not rank Codex and Hermes or establish equal-budget quality.</li>
  <li>It did not prove that every Provider can fit the same durable boundary.</li>
  <li>It did not test malicious Harnesses, poisoned Artifact provenance, or verifier compromise.</li>
  <li>It did not solve multi-Agent branch/join, long-duration compaction, or persistent Session economics.</li>
  <li>It did not establish that every retained object belongs in a shared Protocol.</li>
  <li>It did not test a first-party Ordivon Agent Loop over a bare model API.</li>
</ul>

<h2 id="the-new-question" data-toc="The question after extraction">The question after extraction</h2>

<p>The shared Provider-lifecycle question remains closed. Ordivon subsequently implemented and extracted an independent Harness with Provider-faithful Codex and Hermes adapters, a bounded DeepSeek model–Tool loop, Tool-step checkpoints, recovery, and completion proposals.</p>

<p>The current question is no longer whether version zero can be built. It is whether the thin boundary transfers to another adapter or workload with enough recurring capability and recovery value to justify its permanent cost. See <a href="/projects/harness">the current Harness project page</a>.</p>

<p className="article-closing">H1–H5 retained a boundary, not a platform. The next experiment must earn the first-party Loop.</p>
