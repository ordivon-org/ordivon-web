<div className="article-thesis"><p><strong>Revised · 12 August 2026:</strong> the earlier version described the full execution stack as a 23-step chain. That inventory was useful for architecture work but too expensive as the default explanation. Recent causal-explanation experiments support a smaller public model built around the questions that actually change the next action.</p></div>

<InBrief claim="The path from model output to dependable work is a chain of proof, not a chain of API calls." evidence="E4 · Host/Harness/Runtime/World implementation and cross-project experiments" scope="Current Ordivon work trajectory">
  <p>At each boundary, ask what the previous layer has actually proved. Do not let a successful model call, Tool call, process, or old receipt silently answer a stronger question.</p>
</InBrief>

<h2 id="one-simple-task" data-toc="One simple task">One simple task</h2>

<p>Suppose the instruction is:</p>

<blockquote>Rename <code>timeout_ms</code> to <code>timeoutMs</code>, update callers, run the tests, and ship it if the repository is still in the expected state.</blockquote>

<p>The model can reason about the edit in seconds. But five different questions now appear.</p>

<ol>
  <li><strong>What work is the Agent allowed to attempt?</strong></li>
  <li><strong>What did the Agent actually ask the machine to do?</strong></li>
  <li><strong>What physically happened?</strong></li>
  <li><strong>Did any external consequence occur?</strong></li>
  <li><strong>Does the evidence still justify completing the task now?</strong></li>
</ol>

<p>Those questions are the architecture.</p>

<h2 id="question-one-what-work-is-actually-authorized" data-toc="1. What is authorized?">1. What work is actually authorized?</h2>

<p>A capable model can imagine many useful actions. It should not have to guess which of those actions belong to the current job.</p>

<p>The owning domain or participant defines the objective and consequence. Host preserves the durable work commitment across interruptions. Harness receives one bounded assignment for one Agent episode.</p>

<pre tabIndex={0}><code>{`domain intent
→ durable work commitment
→ one bounded Agent assignment`}</code></pre>

<p>The important distinction is:</p>

<blockquote>Something can be visible to the Agent without being authorized as a consequence.</blockquote>

<p>The Agent needs enough addressable information to distinguish its meaningful legal options. Final authority still belongs to the owner that admits the action.</p>

<h2 id="question-two-what-did-the-agent-decide-to-do" data-toc="2. What did the Agent decide?">2. What did the Agent decide to do?</h2>

<p>This is the Harness layer.</p>

<p>Harness compiles the current working view, calls the model, presents the permitted Tools, returns observations, tracks the bounded episode, and stops when the Run reaches a candidate conclusion, needs input, exhausts its budget, or is interrupted.</p>

<p>There can be two valid paths:</p>

<ul>
  <li>a mature Provider Harness can keep its own native Session and lifecycle;</li>
  <li>Ordivon Harness can provide a first-party model–Tool loop when the Provider supplies intelligence but no complete Agent system.</li>
</ul>

<p>The two paths do not need one synthetic internal event model. They need enough shared evidence to hand durable responsibility back to the caller.</p>

<h2 id="question-three-what-physically-happened" data-toc="3. What physically happened?">3. What physically happened?</h2>

<p>The model says “run the tests.” The Harness asks for a Tool. Neither fact proves that a process started.</p>

<p>Runtime owns that boundary.</p>

<p>It binds exact Workspace state and operation identity to a durable Job and Attempt, then records process state, output, Artifacts, cancellation, timeout, restart recovery, and reconciliation. When immutable inputs or an execution provider matter, those physical commitments become part of the admitted operation.</p>

<pre tabIndex={0}><code>{`Agent Tool request
→ admitted Runtime operation
→ process / file / local system change
→ exact physical evidence`}</code></pre>

<p>If the client disappears after admission, a later Agent should recover the Job rather than infer from missing output that nothing happened.</p>

<h2 id="question-four-did-anything-change-outside-the-machine" data-toc="4. Did the outside world change?">4. Did anything change outside the machine?</h2>

<p>Now imagine the “ship” step calls an external deployment API. Runtime can prove that the local HTTP client process ran. It cannot, by itself, prove what the remote service committed.</p>

<p>This is where provider-native evidence and the narrow World boundary matter.</p>

<p>If the response is lost after dispatch, three outcomes are different:</p>

<ul>
  <li>confirmed success;</li>
  <li>confirmed non-commit or failure;</li>
  <li><strong>UNKNOWN</strong> — the external consequence may have happened, but current evidence cannot establish it.</li>
</ul>

<p>UNKNOWN is not a model mood. It constrains the next action. A blind second POST may duplicate the consequence. The system must reconcile the original operation against the external owner before redispatching when idempotency is not already guaranteed.</p>

<p>World survives where the relationship across independent owners must remain correlated: which external object, which provider action, when the observation became available, and what original consequence remains unresolved.</p>

<h2 id="question-five-is-the-evidence-still-applicable-now" data-toc="5. Is the evidence still applicable?">5. Is the evidence still applicable now?</h2>

<p>The tests passed ten minutes ago. Meanwhile another change landed on <code>main</code>.</p>

<p>The old test receipt can remain perfectly authentic. It can also be insufficient for the current completion decision.</p>

<div className="article-thesis"><p>Historical validity answers “what was true then?” Current applicability answers “may this evidence govern the decision now?”</p></div>

<p>The owning domain or Host-side completion boundary must revalidate the facts that make the evidence applicable: source generation, required Artifacts, unresolved consequences, current authority, and the domain's acceptance conditions.</p>

<p>This is why a completed Harness Run is still only a candidate completion. The work owner decides what the evidence means now.</p>

<h2 id="the-whole-trajectory-in-one-picture" data-toc="The whole trajectory">The whole trajectory in one picture</h2>

<pre tabIndex={0}><code>{`1. domain / participant
   What should happen, and what counts as success?
               ↓
2. Host + Harness boundary
   What durable work is assigned to this Agent episode?
               ↓
3. Harness
   What did the Agent decide and observe?
               ↓
4. Runtime
   What physically happened on the machine?
               ↓
5. provider / World relation
   What happened outside the machine, if anything?
               ↓
6. current owner
   Does this evidence still justify the next semantic consequence?`}</code></pre>

<p>The numbering is explanatory, not a mandatory workflow. Some applications bypass Host. A mature Provider Harness may own more of the Agent episode. A local-only task may need no World relation. The boundaries appear only when their failure class appears.</p>

  <div className="article-data-row article-data-head" role="row"><span role="columnheader">Observed</span><span role="columnheader">Tempting conclusion</span><span role="columnheader">Missing proof</span></div>

<p>Most of the architecture exists to stop these one-step overclaims.</p>

<h2 id="where-persistence-belongs" data-toc="What should persist?">What should persist?</h2>

<p>“Persist everything” sounds safe and usually creates a second problem: more stores, more stale state, more reconciliation, and more old context competing with current truth.</p>

<p>Recent cross-project experiments support a narrower rule:</p>

<blockquote>Persist the smallest responsibility-bearing state whose loss would change current or recoverable responsibility, semantic selection, causal interpretation, recovery, or consequence identity.</blockquote>

<p>A model's intermediate thought does not automatically qualify. A selected Artifact identity may. A durable Task frontier may. The original external request identity under an unresolved consequence may.</p>

<h2 id="where-the-formal-objects-fit" data-toc="Where formal objects fit">Where the formal objects fit</h2>

<p>Once the causal picture is clear, Ordivon's formal names become useful compression rather than prerequisites:</p>

<div className="surviving-stack">
  <div><span>Host</span><strong>Task / WorkingCheckpoint</strong><p>Durable semantic responsibility and resumable frontier.</p></div>
  <div><span>Harness</span><strong>Assignment / Agent Run / Tool continuation</strong><p>One bounded cognitive and Tool-using episode.</p></div>
  <div><span>Runtime</span><strong>Workspace / Job / Attempt / Artifact</strong><p>Exact local physical operation and evidence.</p></div>
  <div><span>World or native provider</span><strong>Observation / external relation / reconciliation</strong><p>Facts that connect independently authoritative systems.</p></div>
</div>

<p>The object names are useful because the responsibilities already exist. They are not evidence that every application needs the same schema.</p>

<h2 id="what-changed-since-the-first-version" data-toc="What changed">What changed since the first version</h2>

<p>The earlier guide tried to be complete by enumerating every step from user surface through model serving, Tool calls, receipts, verification, and graph advancement. The newer Ordivon research suggests a better default: preserve exact detail in source and evidence, but teach the system through the causal questions that change the next decision.</p>

<p>That is not merely an editorial preference. EX3–EX7 compared richer explanation structures against compact causal prose across 1,326 accepted Agent decisions. The richer representations did not improve exact action on the tested surfaces.</p>
