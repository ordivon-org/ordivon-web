# Ordivon Web Design Context

## Purpose

Ordivon Web is human-facing, but its design should not require an Agent to imitate a human designer who manually searches 139 KB of CSS before every change.

The design system therefore exists first as **shared context**:

```text
machine-readable tokens
+ reusable implementation primitives
+ canonical benchmark surfaces
+ explicit design boundaries
        ↓
Agent can compose and modify the Web without guessing the existing language
```

It is not a component bureaucracy and it is not a frozen brand template.

## Current authority

The current design authority is deliberately small:

- [`tokens.json`](./tokens.json) owns the root color, layout, and font-family tokens already used by the live site;
- [`context.json`](./context.json) identifies the reusable primitives and benchmark surfaces an Agent should inspect before inventing another pattern;
- component source files own exact markup, behavior, and local implementation;
- [`aesthetic-research.md`](./aesthetic-research.md) owns how visual alternatives are generated and studied;
- [`evaluation.md`](./evaluation.md) owns the stable evidence hierarchy, blinded preference protocol, and quantitative ranking contract;
- public information hierarchy remains owned by [`../content/editorial/information-architecture.md`](../content/editorial/information-architecture.md).

`styles/generated-design-tokens.css` is a build-local translation of `tokens.json`. It is not an authoring authority.

## Why structured tokens now

Before this slice, the live site already had eighteen root design variables, but they existed only inside `app/globals.css`. That made them convenient for CSS and poor as Agent context: there was no explicit token identity, type, description, or machine entry point.

The token source now follows the Design Tokens Community Group 2025.10 value shapes for color, dimension, and font-family tokens. The Ordivon-specific CSS variable name is retained only as an extension required by the translation step.

This is an extraction of existing design state, not a visual redesign.

## Design layers

### 1. Tokens

Tokens are small shared decisions that already have repeated consumers: canvas/foreground colors, interaction signals, shell widths, article width, and font stacks.

A value should become a token when changing it has coherent cross-surface meaning. Do not tokenize every CSS literal merely because a parser can find it.

### 2. Primitives

A primitive is an implementation pattern worth reusing because it already expresses a repeated public job. Current examples include section hierarchy, publication claim boundaries, the research explorer, and the system explorer.

The registry in `context.json` is an Agent navigation aid. The source component remains the implementation authority.

### 3. Surface composition

A page is not generated by filling a universal card schema. Home, Project, Research, Writing, and Now have different reading tasks and may legitimately use different compositions.

The benchmark surface set exists so an aesthetic or design-system change is tested across unlike public tasks rather than against one attractive screenshot. `evaluation.md` defines how those comparisons are blinded, ranked, and separated from diagnostic metrics.

### 4. Aesthetic experiments

Aesthetic alternatives remain cheap and reversible until evidence earns promotion. Variants may change typography, density, rhythm, geometry, color, motion, or composition without immediately redefining the stable design context.

The design system is **context for generation, not a cage around exploration**.

## Invariants versus taste

These are currently stronger than aesthetic preference:

- content and product state must not be visually encoded in a way that contradicts owner authority;
- information hierarchy must remain understandable without decorative magnitude pretending to be data;
- keyboard, semantic, contrast, reduced-motion, responsive, and long-form reading requirements remain publication concerns;
- generated or experimental visuals must remain replaceable and must not become a second content authority.

These are not permanent aesthetic laws:

- the exact purple accent;
- current grid density;
- current display scale;
- current corner geometry;
- current motion language;
- dark-only presentation;
- any one page composition.

Those may be pressure-tested through the aesthetic laboratory.

## Agent generation rule

Before introducing a new visual primitive, an Agent should inspect in this order:

```text
design/context.json
        ↓
relevant benchmark surface
        ↓
listed reusable primitive source
        ↓
design/tokens.json
        ↓
local page/style implementation only as needed
```

This shortens the cognitive path without hiding the real source.

## Current limitations

N0 structures only the eighteen root tokens that already existed. Semantic node/relation colors in `styles/visual-language.css`, page-specific spacing, type scales, and approximately 139 KB of existing CSS remain partly implicit.

That is intentional. We should migrate repeated design decisions only when Agent generation or aesthetic experiments demonstrate a real shared consumer.

There is currently no Storybook, Chromatic baseline, Figma dependency, or permanent screenshot corpus. Mature external systems show why isolated component states and visual diffs can be valuable, but Ordivon should admit those tools only when the first repeated visual experiment earns them.
